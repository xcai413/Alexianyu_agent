## 上线阻塞与条件

### 1. 多账号回复规则隔离缺陷（当前已复现）

位置：`src/xianyu_agent/domain/message/rules.py:173`。商品为 None 的分支仅限制 `item_pk IS NULL`，没有限制规则属于当前账号或全局。`services/reply_engine.py:105` 将当前入站账号交给该函数，再用其结果选择回复。

复现使用临时 SQLite，不修改真实数据库：建立 A／B 两个账号，各建匹配 `probe` 的账号级规则，B 优先级设为 1、A 为 100；分别让 A 在 `item_id=None` 和商品镜像不存在时匹配。两次均得到：

```text
foreign_rule_present=True
first_rule_is_foreign=True
current_rule_present=True
```

已证明另一账号的模板可以进入并优先命中当前账号的匹配结果；未实际向平台发送消息。触发前提是多个账号存在匹配的启用规则，且入站消息缺少可解析的本地商品镜像。修复与跨账号回归应先于多账号自动回复上线；单账号只读 observe 验证不受这个外发前提影响。

### 2. 管理员退出没有服务端会话撤销（当前已复现）

位置：`interfaces/web/auth/router.py:96` 的 logout 仅删除浏览器 Cookie；`auth/security.py:56` 验证签名与到期时间，没有撤销检查。

用临时签名密钥调用 `issue_session`、`logout`，随后把同一个已复制会话交给 `require_admin`，仍返回 admin。复现结果为 `copied_session_valid_after_logout=True`；没有登录或退出用户的真实浏览器。

触发前提是会话已被复制；这不等于未登录可以访问。当前 TTL 是 8 小时，退出无法立即令副本失效。面向公网的后台需要明确并落实服务端撤销策略；HTTPS、Secure Cookie、入口访问限制也须在目标部署验证。当前 HTTP 本地配置不能作为公网部署配置使用。

### 3. 真实交易与恢复验收没有闭环

- 第六十九轮记录：本地发货任务完成／库存消耗后，用户确认买家未收到，任务随后标为结果不明。第七十轮修订了发送封装，但离线修复不能替代买家收件验收。
- 第七十三轮收到的手机号留资由用户手动点击触发，不能计为本系统自动回复／自动发货成功。
- 第九十七轮已真实只读同步订单时间，并核对 Web 收益／付款／发货报表；这证明镜像与页面在该样本下相符，不证明自动交易链路可用。
- `docs/待真实验证清单.md` 中 B2 断网、B4 Windows 重启、B5 长稳，以及真实自动发货、重复处理库存幂等与结果不明人工收尾仍未完整验收。
- Windows 强杀有历史进程恢复通过记录（`docs/开发计划.md`）；当前 B3 未完成新订阅链路复验。不能表述为“从未做过强杀”，也不能认定当前消息恢复已通过。
- 风控恢复必须以 `SubscriptionReady → confirm_recovered → ONLINE` 为边界；普通 token 刷新不算恢复验收。多实例另需 D1–D4 的业务幂等／接管及 D6 长稳，历史集群健康通过不能替代这些项目。
- AI 自动回复、平台自动化及真实告警投递应分别按清单验收；未验收的能力在首批试运行中保持关闭。

### 4. 生产部署与数据方案尚未就绪

- `Dockerfile:51` 默认运行 `daemon run`；`compose.yml` 没有独立 Web/MCP 服务，也没有发布端口。需要完整安排后台进程、启动／重启和入口代理，不能把镜像里有前端资源或 EXPOSE 8090 当成后台已部署。
- `compose.yml:34` 显式把数据库 URL 设为 PostgreSQL，覆盖 `.env` 中的 SQLite URL；`docs/容器化运行手册.md:75` 中“仅设 SQLite URL 即可复用旧数据”的操作对该 Compose 不成立。
- 当前数据是 SQLite，生产必须先决定保留单实例 SQLite 还是迁移共享 PostgreSQL／MySQL；仓库没有 SQLite → PostgreSQL 数据迁移工具，直接启用默认 Compose 不会自动保留已有账号／镜像。
- Compose 的 PostgreSQL 密码有示例默认值；正式部署应要求显式配置。Cookie 加密密钥与业务密钥必须持久保管，并与数据库／文件备份一起完成恢复演练。本轮未取得实际恢复成功证据。
- 工作区存在未提交修改，尚无冻结候选版本及与其对应的远程 CI、数据库兼容性和容器 job 成功证据。本地 SQLite 通过不能替代目标生产数据库验收。

## 建议执行顺序与验收标准

1. 修复账号规则隔离、落实会话撤销，补充对应回归；对齐只读接口契约并使全量回归全绿。
2. 固定首批部署范围：建议单实例、受控内网、有人值守、observe；落实 Web/MCP 服务、数据库选择、密钥、备份恢复及目标环境数据库／容器检查，冻结发布版本。
3. 用一笔受控真实订单验收：买家确实收件、平台回执与本地审计一致；重复处理只发送一次／扣库存一次；结果不明可人工收尾且不会擅自重发。
4. 在用户安排的维护窗口验证目标环境断网／进程恢复；若生产使用 Windows，补 Windows 重启与消息订阅恢复。随后执行至少 24 小时长稳并检查消息连续性、重复外发、库存、凭据过期、人工接管与告警。
5. 首批只放开已真实验收的能力；多实例与无人值守上线另需相应清单闭环。上述阶段结束后重新评估，当前报告不构成部署批准。
