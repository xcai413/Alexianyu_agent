## 备份范围

`xianyu-agent backup export` 是运营配置导出，不是灾难恢复备份：它不携带Cookie、IM Token、业务主密钥或完整消息／订单历史。这里执行的是数据库与运行目录的完整备份。

本轮备份包含：

- 当前SQLite一致性快照，包括全部46张表（含版本表和SQLite序列表），1个账号、79笔订单、121条消息、库存、发货、审计、风控与其他持久化状态。
- 41个运行文件，包括数据库快照、日志、捕获、二维码、运行配置及本地管理员密码文件；数据库快照以SQLite backup API生成，不直接复制运行中的主库或拼接WAL／SHM。
- 原始 `.env` 及解析后的有效环境值，保留Cookie加密密钥、管理员哈希与会话签名配置。业务密钥版本与旧版本密钥如有配置也应一起保留；本轮没有找到能解密历史SecretVault记录的配置。
- 私有manifest：各文件大小与SHA-256、各表行数与完整内容指纹，用于解包、迁移前后核对，不输出记录正文。

最终完整备份保存在本机 `$HOME/.local/share/xianyu-agent/backups/`，目录权限0700、归档权限0600；具体归档文件名不进仓库。它不是异机备份或自动定时备份的验收结果。

## 手动生成SQLite一致性快照

在项目根目录执行以下命令，适用于当前 `data/xianyu.db` 路径。源库用只读连接，目标文件写入被Git忽略的 `data/backups`；代码不读取或打印凭据。该命令只备份数据库，仍须按上面的完整范围保存运行文件、原环境配置及必要密钥，并验证隔离恢复。

```powershell
uv run python -c "import datetime, os, pathlib, sqlite3; os.umask(0o077); p=pathlib.Path('data/backups'); p.mkdir(parents=True, exist_ok=True, mode=0o700); dst=p/('preflight-'+datetime.datetime.now(datetime.UTC).strftime('%Y%m%d-%H%M%S-%f')+'.db'); src=sqlite3.connect('file:data/xianyu.db?mode=ro', uri=True); out=sqlite3.connect(dst); src.backup(out); assert out.execute('PRAGMA integrity_check').fetchone()[0]=='ok'; out.close(); src.close(); print(dst)"
```

如果数据库路径不同，先明确修改源路径；PostgreSQL／MySQL不能使用此命令。Linux下新目录／文件权限由mode与umask限制，Windows应另配置备份目录的访问权限。

第105轮在保持连接开启的临时WAL库验证：只复制主文件读取到0条记录，backup API快照读取到已提交的1条记录。直接复制主文件不保证包含WAL里的提交，因此真实验收清单已移除该做法；未在真实库上做破坏性演练。

## 隔离恢复方法

1. 把可信归档解包到新的受限目录，用manifest核对每个文件和表内容；保留原归档不变。外部归档应使用安全解包方式，本轮Python使用 `tarfile.extractall(filter="data")`。
2. 从解包结果另做工作副本。验证时只挂载该副本，容器使用 `--network none` 与 `--read-only`；数据库所在挂载目录允许写入以执行迁移。不要挂载真实 `data` 或启动daemon。
3. 恢复原Fernet与业务主密钥及版本配置；不生成替代密钥来掩盖解密失败。将数据库路径与数据目录明确改为副本位置，设 `XIANYU_AUTOMATION_MODE=observe`，关闭外部通知地址，保持账号期望停止。历史业务密钥仍无法解密时保留停用状态并处理原密钥或本地重新录入。
4. 先核对快照，再在工作副本运行当前镜像entrypoint的迁移。本轮迁移验证暂跳过doctor，以便分别记录迁移和诊断结果；之后单独执行完整doctor。新表与版本变化应单列，其他表内容必须仍与manifest一致。
5. 校验Cookie、Cookie快照、IM Token和SecretVault记录解密，只输出计数与失败类别；验证管理员登录、读接口和会话撤销，不进行平台外发。
6. 正式恢复前重新核对目标环境与平台侧订单、发货和库存。快照之后完成的交易不能靠旧快照重建，因此恢复后保持observe，完成对账后再决定开放能力。

本轮容器读取的是解析后的 `effective-env.raw`；`docker run --env-file`与Compose的dotenv处理不同，不要把带单引号的原 `.env` 原样当作Docker原生env-file。原 `.env` 仍完整保存在归档中，供普通CLI／Compose恢复。

灾难恢复旧快照可能丢失快照之后的会话撤销记录。正式启用恢复环境时应另换Web会话签名密钥，让旧Cookie失效；Cookie／IM凭据的Fernet密钥和SecretVault主密钥仍须保留，否则加密数据无法读取。本轮仅在隔离副本保留原签名配置以验证恢复行为，没有轮换真实服务密钥。
