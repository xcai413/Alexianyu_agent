## P0 — WS 常驻与 Windows 自恢复

### P0 目标

- 一个常驻 daemon 管理所有已启用账号,每个账号一个独立 asyncio Worker。
- daemon 不使用 `--seconds`;持续运行直到收到明确停止请求或操作系统关闭信号。
- CLI、TUI、MCP 不直接持有长期 WS 连接,通过持久化控制面向 daemon 发命令并读取状态。
- 同一数据目录只允许一个有效 daemon,避免重复登录和重复回复。
- 进程崩溃和 Windows 重启后可由 Windows 任务计划程序拉起。

### 当前运行链路

```text
CLI / TUI / MCP
       │ 写入命令、读取状态
       ▼
SQLite 控制面(worker_commands / daemon_instances / worker_status)
       │ daemon 周期性协调
       ▼
RuntimeDaemon ──> AccountPool ──> AccountWorker × N ──> 闲鱼 WS
       ▲
       └── Windows 主任务 + 每分钟 Watchdog 负责启动与故障恢复
```

`worker_status` 继续记录实际连接状态;P0.1 已新增 daemon 实例状态,P0.2 已新增账号级
控制数据:

- `desired_state`:用户期望的 `running/stopped`。
- `actual_state`:Worker 实际的 `connecting/connected/reconnecting/disconnected/error`。
- `worker_commands`:跨进程 `start/stop/restart` 请求及其执行结果(P0.2 已实现)。
- `daemon_instances`:daemon 实例、PID、版本、启动时间、心跳、停止/重启请求和最后错误
  (P0.1 已实现)。

`daemon_instances` 已由迁移 `4dc9fbc82a37` 固定;`desired_state` 与 `worker_commands` 已由
迁移 `9a7e615f2c41` 固定。

### P0.1 — daemon 核心

状态:**代码完成,待 P0.5 完整真实验收。** 已实现 `daemon run/status/stop/restart/logs`、
`daemon_instances`、单实例文件锁、账号启用状态对账、优雅退出与轮转脱敏日志。

交付:

- 新增常驻运行协调器,启动全部 `enabled=true + desired_state=running` 的账号。
- 定期对账账号配置,动态启动、停止或重启对应 Worker。
- 处理 Ctrl+C、Windows 关闭信号和正常退出,确保 Worker 与数据库连接有序关闭。
- 使用单实例锁和数据库心跳共同识别重复 daemon;PID 不能作为唯一依据。
- daemon、Worker 与协议日志统一写入 `data/logs/`,Cookie、Token 和消息敏感字段必须脱敏。

计划命令:

```powershell
uv run xianyu-agent daemon run
uv run xianyu-agent daemon status
uv run xianyu-agent daemon stop
uv run xianyu-agent daemon restart
uv run xianyu-agent daemon logs --tail 100
```

### P0.2 — 跨进程账号池控制

状态:**代码完成并通过真实账号短时验收。** 已实现 `accounts.desired_state`、
`worker_commands`、daemon 命令领取/执行/回执和 `pool start/stop/restart/start-all/stop-all`。

交付:

- `pool start/start-all/stop/stop-all/restart` 写入持久化命令,由 daemon 执行。
- CLI 可等待命令完成并返回实际结果;超时不伪造成功。
- daemon 不在线时,命令明确返回“未执行/等待 daemon”,不再只改一行状态后显示成功。
- 每个账号独立重连与熔断,单账号异常不能结束整个 daemon。
- `FAIL_SYS_USER_VALIDATE` 进入持久化人工验证熔断：该账号停止自动重试，冷却结束后仍需一次成功的
  `auth refresh` 才能恢复；该机制不做验证码绕过、Cookie 自动续期或网络/设备伪装。

命令语义已从“前台进程/DB 标记”切换为“控制常驻 daemon”。当前准确接口以
`docs/api-reference.md` 为准。

### P0.3 — Windows 启动与自恢复

状态:**代码完成,P0-C 真实强杀恢复通过;P0-D Windows 重启待验收。** 采用 Windows
任务计划程序,不引入第三方服务包装器。当前命令:

```powershell
uv run xianyu-agent service install
uv run xianyu-agent service start
uv run xianyu-agent service stop
uv run xianyu-agent service status
uv run xianyu-agent service uninstall
```

要求:

- 已实现 `XianyuAgent-Daemon` 主任务和 `XianyuAgent-Watchdog` 每分钟巡检任务。
- 后台隐藏运行,工作目录和 `pythonw.exe` 使用安装时解析出的绝对路径。
- 默认当前用户登录后启动;`--startup system` 提供需管理员权限的系统启动模式。
- Watchdog 以统一健康判定检查数据库状态、90 秒心跳和 PID,不健康时拉起主任务。
- `service stop` 写入 `data/runtime/service.paused`,人工停机不会被 Watchdog 误判为故障。
- `service install` 默认保持暂停,只有显式 `--start-now` 或后续 `service start` 才运行。
- `install/uninstall` 会修改 Windows 系统状态,只在用户明确授权后执行。

### P0.4 — 健康检查与可观测性

状态:**代码完成并通过正式运行库只读验收。** 交付:

- `daemon status` 展示 daemon 心跳、PID、运行时长、版本和每账号实际状态。
- daemon 心跳超过 90 秒未更新时标记为 stale,而不是 online。
- `doctor` 检查数据库可写、迁移版本、加密密钥、账号 Cookie、日志目录、重复实例与任务计划状态。
- `daemon logs --tail N` 读取脱敏后的本地日志。
- TUI 增加 daemon 总状态、期望/实际状态差异和 stale 告警。

当前证据:`doctor` 正式运行结果为 8 PASS / 1 WARN / 0 FAIL;WARN 是已停用 `demo`
账号保留的不可解密旧 Cookie,未删除。TUI 正式库渲染为 daemon online、漂移 0、
在售商品 10,`xcaicai` 为 running/connected/一致。

## P1-P6 后续范围

### P1 — 真实入站消息校准

- 用测试买家向已登录账号发送文字消息,记录原始帧的脱敏 fixture。
- 校准消息类型、message_id、chat_id、buyer_id、item_id、时间戳和正文路径。
- 验证重复帧幂等、断线补帧和系统通知不会被误识别为买家消息。

代码前置(2026-08-14 已完成,待真实校准):

- Cookie 换取 IM accessToken;Token 以 Fernet 密文缓存,设备 ID 稳定复用。
- `/reg` 与 `/r/SyncStatus/ackDiff` 初始化成功发送后才标记 `connected`。
- `/reg` 已增加相同 mid 的服务端确认门;确认响应 ACK 后才发 `ackDiff`,超时或明确拒绝
  均不标记 connected。
- 推送先 ACK,再解包 `syncPushPackage`;支持 Base64 JSON 与 MessagePack。
- 真实聊天字段映射、账号级消息幂等、系统提示隔离和默认 `observe` 模式已由离线测试覆盖。
- 本地集成测试已覆盖断线重连后服务端重放同一 `message_id`,SQLite 仍只保留一条消息。
- `auth qr-login` 保存新 Cookie 后立即强制换取并加密缓存 IM token;换取失败返回非零,
  `auth refresh` 仅作为后续重试/诊断命令。`auth qr-login/login` 会使旧 token 失效但保留
  稳定设备 ID;账号级跨进程锁禁止 Worker、登录、刷新、capture 重复占用同一账号。
- `protocol capture` 以前台观察模式捕获真实推送,只落库标准字段,原始结构中的 Cookie、
  Token、身份、会话、商品和正文值均不可逆脱敏后写入 `data/captures/`。
- `protocol capture-verify` 不只读取 summary,还会用实际 state/frame/event/error 记录交叉
  核对统计,并扫描任意层级(包括数字协议键)的未脱敏字符串。

### P2 — 商品运营配置

- 为 `items` 增加本地运营配置,不修改闲鱼端商品。
- 支持商品级回复模式、规则集、卡密绑定、自动回复/自动发货开关。
- 新配置默认关闭自动动作,所有变更写审计日志。

### P3 — 真实消息发送与 ACK

- 从真实会话校准发送帧、必要请求头/参数及 ACK。
- “已发送”只以平台确认或可验证回执为准;超时和拒绝进入失败/待确认状态。
- 先提供人工触发 `message send`,通过后再接规则引擎。

### P4 — 真实订单与人工确认发货

- 先执行 `order sync --account <id>` 的真实只读校准，确认订单 API、分页、订单 ID、商品 ID、
  状态和数量字段；校准失败时不进入发货流程。
- 校准真实订单创建、支付、取消与退款事件。
- 先实现“订单入库 → 人工确认 → 原子扣卡 → 发送 → 回执 → 审计”。
- 未确认、金额超限、库存不足或状态不明确时禁止自动发货。

### P5 — 单商品自动运营

- 每次只给一个低风险商品启用自动回复或自动发货。
- 观察频率限制、静默时段、失败熔断和库存告警后再逐项扩面。

### P6 — 多真实账号长稳

- 接入第二个真实账号,验证独立 Cookie、Worker、日志、限流与熔断。
- 验证单账号掉线、Cookie 失效或风控不会拖垮其他账号。
- 完成至少一次 24 小时多账号并行运行并保存统计证据。

## 阶段纪律

- 每个优先级完成时暂停开发并 review,不跨过未完成的真实验收。
- mock 测试、真实账号测试和 Windows 自恢复测试分别记录,互相不能替代。
- 自动回复与自动发货默认关闭;真实外发动作必须在相应阶段获得明确授权。
- 不实现滑块自动求解、Cookie 自动续期、Web 管理后台或绕过平台风控。
- 代码可以本地提交;只有用户明确说“推送”时才推送到 GitHub。
