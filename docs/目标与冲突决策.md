## 一、最终形态(用户 2026-09-19 定稿)

一个**人类与 Agent 共治**的闲鱼运营系统,最终以**可持续无人值守运行**为交付标准:

1. **无人值守为核心**:登录态自动续期、断线自恢复、失败熔断;需要人工处理时最小化打扰,
   处理完能自动恢复该账号,不影响其他账号。
2. **Web 管理后台**:以 23Star/xianyu-super-butler 为基准独立实现(AGPL-3.0,只做 UX 与
   业务规格参考,不复制源码)。
3. **Agent 实时监控与介入**:无人值守期间,Agent 可通过 MCP 或 CLI 观察状态并执行介入动作。
4. **冲突处理**:实现与既有 issue / 文档冲突时,先登记到本文件,由用户决策。

仓库 README 的一句话描述("为 AI Agent 直接控制、可持续无人值守运行的轻量化闲鱼运营系统")
与本目标一致;Issue #9(Full Web Operations Console,Super Butler UX 基准)已经是 Web
后台的既定条目。

### C5 — "无人值守"与"平台要求人工验证"的边界:**需要明确定义**

- 事实:平台可以随时要求人工验证。不做绕过的前提下,无人值守**不可能**意味着"永不需要人"。
- 建议的系统契约(待用户确认):
  1. 尽可能少触发(请求节流与抖动、避免重试风暴);
  2. 触发后立刻熔断该账号、其他账号不受影响;
  3. 把可操作的信息交给人类(验证链接 / 重新登录指引);
  4. 人工处理后自动恢复该账号,无需重启 daemon;
  5. 全过程对 Agent 可观测(MCP/CLI 能看到状态与原因)。

## 三、决策结果(用户 2026-09-19)

### C2 — 滑块自动求解:**做,含重试与人工兜底**

- 决策:实现自动滑块能力;**必须有重试机制**;无法通过时,**通过通知通道提醒人类解锁**。
- 实现契约(据此执行):
  1. 只对平台明确给出的验证挑战发起求解(例如 punish 惩罚链接这类响应),
     不主动探测;
  2. 重试有限次并**递增退避**,绝不出现"每分钟数百次"的重试风暴(参考项目曾因此两小时未恢复);
  3. 用尽重试仍失败 → 熔断该账号、把惩罚链接与指引交给人类、其他账号不受影响;
  4. 人工处理完成并成功刷新后,该账号自动恢复。
- 待办依赖:需要浏览器自动化栈(参考实现用 Playwright 生成拖动轨迹);仓库当前无该依赖,
  引入需评估体积与可测性。参考实现同时记录了"自动求解可能无效"的实测,因此本能力必须
  按上面的兜底设计实现,不能作为无人值守的唯一手段。

### C3 — 浏览器指纹:**窄口径与宽口径都做,带优先级与退避**

- 决策:窄口径(转发真实浏览器标识头)与宽口径(真实浏览器指纹/隐身栈)都要,并**设立优先级
  与退避规则**;两者都失败时**通知人类**。
- 实现契约:
  1. 默认走窄口径(成本低、风险低),在请求头层面转发真实浏览器标识;
  2. 遇到验证挑战或风控拒绝时,按优先级升级到宽口径(浏览器指纹栈),升级本身也受退避与
     冷却约束;
  3. 两档都失败 → 熔断 + 通知人类;
  4. 过程中记录使用了哪一档(审计可查)。

### C5 — 无人值守与人工验证的边界:**先自动处理,失败后通知人类**

- 决策:先自动处理;无法通过再通知人类。
- 实现契约:自动处理包含"续期 → 重连 → 求解/升级指纹 → 重试";上述手段用尽即熔断该账号、
  通知人类、保留可操作信息;人工处理后该账号自动恢复,daemon 无需重启;全过程对 Agent 可观测。

### C6 — Agent 介入边界:**采纳建议**

- 读与恢复类动作(查看状态/熔断原因/队列/审计、暂停与恢复账号、重试失败项、查看回复决策)
  Agent 可自主执行。
- 涉及真实外发与资金的动作(发送消息、发布/改价/上下架、发货)必须人类确认,通过显式确认门
  执行(现有 confirm/--yes 门即为此设计)。

### C7 — 容器化与多副本:**允许多副本(2026-09-20 确认)**

- 决策:最终交付容器化部署,不限定单容器,允许多副本横向扩展。
- 实现契约:多副本下「同一账号任一时刻最多一个未过期 owner」;跨副本互斥使用数据库租约,
  文件锁降级为副本内二级保护;多副本必须使用 Postgres;容器语义的验收单独记录,不覆盖既有
  Windows 场景结论。
- 分期、数据模型与验收标准见 `docs/容器化与多副本方案.md`(M0–M5)。

## 四、由此产生的实现顺序

1. **续期接入**:静默续期接进 CredentialSupervisor(读加密 Cookie → 续期 → 成功写回并热恢复;
   熔断期间不续期),并实现 refresh_after 提前刷新与调度——无人值守的核心。
2. **风控地基**:请求节流与抖动、递增冷却、惩罚链接与指引的人工转交、审计与可观测
   (供 C2/C3 的兜底复用)。
3. **通知通道**:通知人类的出口(Issue #8 的 Notification 范围);在此之前先落到审计 +
   CLI/TUI/Web 可见,避免"通知了但没人看见"。
4. **指纹两档**:窄口径先做(请求头),宽口径需浏览器栈。
5. **滑块求解**:按 C2 契约实现;需引入浏览器自动化依赖。
6. **Web 控制台**:按 Issue #9(Super Butler 基准)单独出分片计划。
7. **容器化与多副本**:按 `docs/容器化与多副本方案.md` 的 M0–M5 分期执行;M0(打包层)不动核心。

### C8 — 功能优先级调整:**自动发货与买家侧自动化优先(2026-09-20 用户决策)**

- 决策:商品发布相关功能降为低优先级;自动发货、发货调用外部 API、自动擦亮、自动要小红花
  提到高优先级。
- 与既有文档的差异:`docs/阶段计划-Phase6.md` 写着「本阶段不做:自动评价(#6)」,
  `docs/验证记录.md` 记录「擦亮尚未实现,缺少接口证据」。本条覆盖前者;后者仍受"不臆测协议"
  约束,不能凭印象实现。
- 实现契约:
  1. **自动发货**:复用既有 `DeliveryExecutor` / `DeliveryJobService` / `AccountWorker.
     _deliver_paid_order` 链路,不新造发货实现;Web 先提供只读 Dry Run 预览,真实外发必须显式确认;
  2. **发货调用 API**:复用既有 `ApiDeliveryProvider`(出站守卫 → SecretVault → 模板渲染 →
     结果分类),Web 侧只做配置可见性与预览,密钥值永不回显;
  3. **自动要小红花**:走既有外发链路向买家发送邀评文案,必须幂等(同一订单只邀一次)、
     受频控与静默时段约束、可审计;不实现任何"代买家评价"的写接口;
  4. **自动擦亮**:必须先拿到协议证据(接口名、签名参数、频控)再实现;在证据到位前,只登记
     需求与待办,不写猜测性代码;
  5. 上述四类都涉及真实平台动作,首次验证一律由用户执行,步骤写入 `docs/待真实验证清单.md`。
- 优先级顺序(高 → 低):自动发货 → 发货 API → 自动要小红花 → 自动擦亮 → 商品发布。
