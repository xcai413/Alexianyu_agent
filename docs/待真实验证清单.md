# 待真实验证清单

> 用途:列出**必须在真实环境执行**的验证点。离线测试(`uv run pytest`)、本地 mock 与 CI 都不算数。
> 用法:每条含【前置】【命令】【期望】;测完把结论写进 `docs/验证记录.md`,并把这里的 `[ ]` 改成 `[x]`,注明日期。
> 规范:不把二维码、Cookie、Token、Fernet 值、订单号、买家资料、卡密或日志提交进仓库。

## 0. 建议的执行顺序(给执行人)

整份清单有 30 多条,但**不要按编号顺序盲跑**:有些条目会改变平台状态,有些需要特定前置。
推荐顺序如下,每一步都能独立回滚或停手。

### 第 0 步:开跑前的准备(必做)

1. **确认长稳已结束**:`uv run xianyu-agent soak status` 显示已停止;D6 长稳期间不要做任何真实动作。
2. **完成一致性备份**:SQLite使用[备份与恢复验收](备份与恢复验收.md)中的backup API快照命令，不直接复制运行中的主库；同时保存运行文件和原密钥配置。PostgreSQL部署使用对应数据库导出并补目标后端恢复验证。
3. **确认默认关闭**:`grep XIANYU_AUTOMATION_MODE .env`(应为 `observe`)。整份清单只在"要发真实动作的那一条"里
   临时改成 `active`,做完立刻改回。
4. **准备测试物料**:一个自己可控的测试买家号、一笔自己下单的订单、一张 https 公网小图、
   一个只服务测试环境的发卡接口(如果要做 F4)。
5. **每条做完就记录**:把命令、时间、脱敏后的结果写进 `docs/验证记录.md`,并把本文件的 `[ ]` 改成 `[x]`。

### 三条硬性纪律

- **一次只开一个动作**:需要 `active` 的条目前后都要改回 `observe`,不要整段都开着。
- **结果不明不重试**:任何命令返回"结果不明"时,先按对应条目里的"怎么核对"检查平台,
  确认没发生再重跑;`uncertain` 的任务用 `xianyu-agent attention list` 找到并人工收尾。
- **改价、发货、发消息只用测试对象**:不要拿真实买家的订单当试验品。

## A. 账号与协议(P1)

### [~] A1 熔断恢复(历史路径通过,新会话探针待复验)
- 前置:账号触发 `FAIL_SYS_USER_VALIDATE`。
- 命令:App 内人工完成验证 → `uv run xianyu-agent auth refresh -a <账号>`。
- 期望:命令建立被动 WebSocket 会话并等到 `ONLINE` 后输出「验证熔断已解除」;
  成功后 `auth status` 不再有 `ws_risk_*` 三行;失败时风控闸门保持开启。
- 跨副本检查:恢复期间其他实例不得获取同一账号租约;失败或取消后租约应释放。
- 备注:2026-09-19 的历史证据只证明旧版 Token 刷新路径,不覆盖本次新增的真实会话探针。

#### 风控恢复故障的最小证据

由用户记录实际故障,不主动诱发风控,不自动求解验证码。测试期间禁止自动回复、发货和运营外发。

| 证据 | 用于区分的问题 |
|---|---|
| 首次错误码、发生时间与所用项目版本 | 平台要求人工验证、限流或程序错误,不能仅凭“风控”概括 |
| App 验证完成时间及平台提示（脱敏） | 验证是否真正完成,还是仅打开验证页面 |
| 刷新前后 `auth status -a <账号>` 与 `auth refresh` 退出码、输出 | 本地冷却、凭据失败、租约拒绝与会话订阅失败 |
| 恢复期间风险事件、最终 Worker 状态及实例数量 | 是否仍处于 NEEDS_VALIDATION,是否存在并发实例 |
| 新会话建立后用户在平台核对的收发结果 | ONLINE 仅证明连接就绪,不能替代消息送达证据 |

不得提交 Cookie、Token、完整响应体或未脱敏聊天正文。上述证据缺失时,只能记录代码侧已确认的缺陷,
不能把它们当作用户真实故障的根因。账号正处于 soak 时只读状态,不要停止服务或运行恢复探测。

### [ ] E5 结果不明的发货任务人工收尾
- 背景:发送过程中连接中断(`uncertain`)时,自动流程既不当成功、也不当失败,任务与库存都会被冻结。
  收尾路径必须可用,否则卡密会永久冻着。此前 `delivery job resolve` 被错挂成 `plan`,这条路径实际是死的,
  已于本轮修好并加了防回归断言。
- 命令(先用一条**非** uncertain 的任务验证拒绝路径,安全且不需要真实故障):
  1) `uv run xianyu-agent delivery job list` 找到一条 `completed` 或 `failed_retryable` 的任务 id;
  2) `uv run xianyu-agent delivery job resolve <id> --delivered --note '测试依据' --yes`;
  3) `uv run xianyu-agent delivery job resolve <id> --delivered --note '' --yes`(空依据)。
- 期望:第 2 步被拒绝并提示「不是结果不明,无需人工收尾」,且不写审计、不改状态;第 3 步被拒绝并提示
  「必须写明依据」。这两步都不会碰真实订单,可以放心在真实库上跑。
- 真实故障路径(可选,发生 `uncertain` 时再走):`delivery job show <id>` 核对平台订单页 →
  `delivery job resolve <id> --delivered|--not-delivered --note '<核对依据>' --yes`,期望任务状态变为
  `completed` / `failed_retryable`,**库存同时核销或退回**(`inventory reservation show <预留 id>` 可核对),
  并且 `audit_logs` 里有一条 `delivery.job.resolved`(只记判定与库存去向,不记依据正文)。
- 注意:`resolve` 只改本地事实,不触发任何平台动作,所以不需要 `active` 模式,也不占用平台调用额度。

- 现状:本轮新增多渠道通知(`notify channel *`、`notify messages`、Web 通知页,迁移 `c3f7a52e9b14`)。
  协议无关:它只往运营自己配置的 https 地址 POST,不碰闲鱼接口,所以不需要平台校准,但仍过出站守卫。
- 原理:钉钉/飞书的消息形状与加签算法按各自文档实现并有离线断言(签名逐字节比对),telegram 用
  `bot<token>/sendMessage`,bark 用 `<server>/push` + `device_key`。密钥只以 SecretVault 引用入库。
- 前置:准备一个自己的机器人地址(钉钉/飞书自定义机器人、telegram bot 或 bark server 均可)。
- 命令:
  1) `uv run xianyu-agent notify secret add --label smoke`(粘贴机器人密钥或签名 secret,记下输出的引用名)
  2) `uv run xianyu-agent notify channel add -n smoke -k dingtalk -t <https webhook 地址> --secret-ref <上一步引用>`
  3) `uv run xianyu-agent notify channel test <渠道 id 或名称>`
  4) `uv run xianyu-agent notify channel list` 与 `uv run xianyu-agent notify messages`
- 期望:第 3 步返回 OK,手机上能收到一条测试消息;第 4 步的列表里地址只显示 `https://<主机>/…`,
  密钥列只显示引用名;`notify messages` 里能看到这次 `account_risk/test` 记录。
- 反向验证(同样重要):把地址改成 `http://` 或内网地址(如 `https://127.0.0.1/hook`)应当**建不进去或被拒绝出站**
  (`BLOCKED:outbound_guard`);删掉 SecretVault 里的密钥后 `uv run xianyu-agent doctor` 应当把
  `notification_channels` 报成 FAIL。
- 通过后:保留渠道用于真机验收期间的通知(发货结果不明、风控待验证都会推过来),并把结论写进
  `docs/验证记录.md`。

### [ ] N2 daemon 自动派发(依赖 N1)
- 前置:N1 已通过,库里至少有一条启用的通知渠道;`.env` 里 `XIANYU_ALERT_WEBHOOK_URL` 留空。
- 命令:`uv run xianyu-agent daemon status`(确认 daemon 在线),然后人为制造一条待办(例如把某个
  测试订单置为需要确认,或等一条真实 `uncertain`),观察通知与 `uv run xianyu-agent notify messages`。
- 期望:每条事项在**每个渠道**只发一次(重复跑 `notify messages` 不应出现第二条同样的记录);
  同时配了 `XIANYU_ALERT_WEBHOOK_URL` 时,库里已有启用渠道的情况下**不应**再走环境变量那条路。

### [ ] N3 AI Provider 真实调用(`ai test`)
- 现状:本轮新增 `ai test`(对照 butler 的 `/ai-reply-test`)。它**真的调一次你配置的模型**
  (会消耗额度),但不会发给买家、不写消息镜像、不写回复记录。
- 前置:至少一个 Provider 已配置密钥并 `ai enable`;`uv run xianyu-agent ai list` 能看到启用状态。
- 命令:
  1) `uv run xianyu-agent ai test --message 还在吗`(最小连通性)
  2) `uv run xianyu-agent ai test --message 便宜点 --account <账号> --item-id <商品 id>`(带本地上下文)
- 期望:第 1 步打印模型名与一条草稿,并以「这条草稿会通过输出安全闸」结尾;若模型回了站外联系方式,
  命令应报「会被输出安全闸拦截」「站外联系方式」并以非零码退出——这正是我们要它做的事。
- 反向验证:把密钥置为无效(`ai rotate-key`)再跑一次,应当报「调用失败」且**不回显密钥或请求细节**;
  把回复模式改回 `RULE_ONLY` 再跑,应提示"当前模式不会调用 AI",但仍能测通 Provider。
- 通过后:把结论写进 `docs/验证记录.md`。这一项与闲鱼平台无关,不需要 `active`,也不会碰任何买家。
