# 参考项目功能对齐矩阵

本文件把两个既定参考项目的功能逐项对照到本项目,并给出移植决策。它回答两个问题:
参考项目有什么、我们打算怎么对齐。协议类事实另见 `docs/protocol-notes.md`,
真实验收步骤另见 `docs/待真实验证清单.md`。

对照来源(只做只读核对,不复制源码):

- `xcai413/Ydisks-Xianyu-Helper`(Apache-2.0):Go 实现,含 `internal/automation`、
  `internal/xianyu/mtop`、`internal/server` 三块。
- `xcai413/xianyu-super-butler`(AGPL-3.0):Python + React 实现,含 `app/reply_server.py`、
  `XianyuAutoAsync.py`、`utils/`。

## 0. 不移除的本质(移植红线)

移植任何功能都必须满足以下约束,与参考实现的做法冲突时以本仓库为准:

1. **CLI 是单一事实源**:Web、MCP、TUI 只包装 CLI 已经具备的能力,不各自实现业务。
2. **分层不破**:`domain` 无 IO,`application` 编排,`infrastructure` 落库与外部调用,
   `protocol` 只做协议 IO。
3. **默认安全**:外发分两级,任何一级都不允许"顺手发一下"。
   - **自动路径**(自动回复、自动发货、定时擦亮/求花):`observe` 下严格空操作,开启真实动作要同时
     满足显式 `active`、动作已真实校准、动作已启用三道门禁。
   - **人工单次路径**(`item polish --yes`、`order adjust-price/confirm-shipment/request-flower`、
     `message send --yes`、`message send-image --yes`、`message report-read --yes`、
     `delivery job run --send --yes`、Web 的 `confirm` 弹窗):不受 `observe` 限制,但必须逐次显式确认,
     并且绝不从自动流程调用。这条区分是写下来的约定,不是漏判——`observe` 管的是"机器能不能自己动手",
     管不了"人已经决定动手"。
4. **失败分类**:确定未发出可重试,明确拒绝是终态,结果不明一律冻结且不自动重发。
5. **密钥与敏感数据**:Cookie / Token / 卡密明文不进日志、审计、接口响应;只走加密库与掩码预览。
6. **不做能力**:滑块自动求解、验证码绕过、设备指纹伪造、代买家评价。

## 6.1 参考项目有、我们有意不做的服务侧能力

| 参考能力 | 来源 | 这个仓库的现状与理由 |
|---|---|---|
| 闲鱼账号密码登录 / 自动续期 | Helper `/api/v1/password-login`、`admin/password` | **有意不做**。参考实现要用无头浏览器 + 远程打码完成验证,正好落在既定非目标(滑块/验证码)里;我们的续期是 `long-login` 换 token,失效后要求人工扫码重登。代价写明白:会话彻底失效时需要人扫码,不能全凭密码无人恢复 |
| 多用户 / 角色 / 每人主题设置 | Helper `/api/v1/admin/users`、`settings/user` | **有意不做**。这是单操作者自托管系统,一个管理员会话足够;多用户会引入邀请、权限、改密一整套表面,与"最小暴露面 + 密钥只走加密库"相反 |
| 界面可写的系统设置 | Helper `/api/v1/settings/system`、`session/*` | **有意不做**。配置的事实源是 `.env` + CLI,界面只读;可写的系统设置等于第二份配置真相 |
| 管理统计 / 任务面板 | Helper `/api/v1/admin/stats`、`admin/tasks` | 已覆盖:`analytics report`、`daemon status`、`automation runs` 三处合起来就是同一批事实,不另开一份统计 |
| 自动化问题清单 | Helper `/api/v1/automation-issues` | 已覆盖:`attention list` 把发货任务、平台动作、账号风控合成一个待办清单 |
| 关键词搜索市场行情 | butler `/items/search`、`/items/search_multiple` | 参考实现用 Playwright 打开搜索页并拦 `mtop.taobao.idlemtopsearch.pc.search`,还要挂远程打码服务 | 有意不做:它依赖的正是我们排除的浏览器池/验证码能力;要做得先用真实抓包证明有纯接口可用 |
| 关键词导入 / 导出 | butler `/keywords-import/{cid}`、`/keywords-export/{cid}` | 已覆盖:回复规则用 CLI 管理(`rule add/list/...`);不引入第二套导入导出格式,需要批量时用 `backup export/import`(备份含回复规则) |
| 日志清空 / 缓存重载 | butler `/logs/clear`、`/system/reload-cache` | 有意不做:日志要留证,缓存不在这套进程模型里(每个事件都从库读) |
| 本地数据修补(卡密/已发布 id/短链)| butler `/product-automation/repairs/*` | 有意不做:那是修参考项目自己写坏的数据;我们的写入都过状态机,用 `doctor` + 审计定位而不是批量改库 |

## 7. 明确不做

| 参考能力 | 来源 | 原因 |
|---|---|---|
| 滑块自动求解 / 浏览器池 | butler `browser_pool`、`slider_*` | 既定非目标,规避平台风控对抗 |
| 验证码远程打码 / 人脸验证截图 | butler `captcha_remote_control`、`face-verification` | 同上 |
| 代买家评价 | 双方评价接口 | 参考冲突且不可撤销,见 `protocol-notes.md` §10.3 |
| 设备指纹合成 | butler `slider_patch` | 既定非目标 |

平台写动作的 **Web 入口边界**(有意为之,不是漏做):界面只保留三类人工写操作——人工回复
(`/conversations/{chat_id}/reply`,要有 `takeover` 与 `confirm`)、真实发货
(`/delivery/run`,要先 Dry Run 放行再输入订单号确认)、发货任务人工收尾
(`/delivery/jobs/{id}/resolve`)。擦亮、求花、订单改价、平台确认发货、已读上报、图片消息这些**单次校准
入口只在 CLI**:校准的产物是"可复制的完整命令 + 输出 + 平台侧核对",一个点一下就发出去的按钮既留不下
这份证据,也更容易被误点。要做真实动作必须能在命令行里贴出来。

## 8. 执行顺序

1. 卡券与发卡源补全(GET 取卡、试调用、卡券导入查看)。
2. 发货模板库。
3. 订单改价(待付款订单)。
4. 备份导出 / 导入。
5. 日志、风险日志与通知展示。
6. 账号任务与自动化规则补全(含人工介入 resolve)。
7. 商品级自动化(素材、筛选、删除规则)。
8. 分析面板。

每一项完成后:补迁移(如需)、CLI(单一事实源)、Web 包装、离线测试,并把真实平台动作
登记到 `docs/待真实验证清单.md`,由用户执行真机验收。

### 2026-09-21 剩余项的证据复核(不做移植的决定与理由)

逐一检查后,剩下四项都不能在"不臆测协议"的前提下移植:

| 项 | 来源 | 为什么现在不做 |
|---|---|---|
| 免拼/免运费发货 `mtop.idle.groupon.activity.seller.freeshipping` 1.0 | super-butler `secure_freeshipping.py`(单一来源) | 参考实现的请求体把 `itemId` 直接拼接成**不带引号的裸值**,只在该字段恰好是数字时才成立;`bizOrderId`/`buyerId` 的引号写法也不一致。照抄会在字段类型变化时发出非法 JSON,自己"修正"则是猜类型。同时它对**任何**失败(含业务错误与网络异常)都立即递归重试,与我们的"结果不明不重发"相反。需要真实抓包确认字段类型与幂等语义后再实现。 |
| 评价买家 `mtop.taobao.idle.rate.create` 4.0 / `mtop.taobao.idle.merchant.rate.create` 1.0 | Helper 与 super-butler 各一版本 | 两个参考项目**接口名与版本都不一致**,且评价提交后不可撤销;`protocol-notes.md` §10.3 已登记为暂不实现,需要用户决策。 |
| 待评价列表 `mtop.taobao.idle.merchant.rate.list` 1.0 | Helper(单一来源) | 只读且可用,但它的唯一用途是驱动"评价买家";在评价写入未被决策前单独移植只增加一个悬空能力,先不做。 |
| 商品编辑/上下架写入 | 两个参考都没有公开接口 | Helper 的发布接口 `mtop.idle.pc.idleitem.publish` 是创建用途,payload 里没有编辑既有商品的字段;super-butler 的 `/items` 只是本地手工登记。没有证据就不实现。 |

结论:参考项目里**有可用证据**的功能已经全部移植完毕;剩下的四项要么证据自相矛盾,要么需要用户在参考冲突中做决定。
