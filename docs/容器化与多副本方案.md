## 一、范围

纳入:

1. 单容器自托管部署,数据库使用 Postgres。
2. 多副本横向扩展:同一账号在任一时刻最多由一个副本持有 WS 会话。
3. 支撑以上两点的数据模型、并发原语、观测、健康检查与验收方法。

不纳入(需用户决策后再登记):

- 多租户/多店铺隔离(当前 `accounts` 是单 owner 模型)。
- 引入 Redis 或消息队列(先只用数据库租约)。
- Web 管理后台(Issue #9 另行处理)。

### 2.4 单实例假设清单(多副本阻塞项)

| 编号 | 现状 | 多副本后果 | 位置 |
|---|---|---|---|
| B1 | `daemon.run()` 先抢单例文件锁;`_start()` 无条件把所有 active 实例标 `error`,并把所有 RUNNING 命令标失败 | 共享卷时第二个副本起不来;分开卷时副本互相把对方标成异常、把对方正在执行的命令判失败 | `runtime/daemon.py::run/_start`、`domain/runtime/daemon.py::mark_orphaned_active`、`domain/runtime/command.py::fail_stale_running` |
| B2 | `reconcile_desired_accounts()` 在本进程拉起全部 `desired_state=running` 账号;账号互斥只靠文件锁 | 每个副本都会尝试连同一账号;文件锁跨容器无效,NFS/CIFS 上尤其不可靠 | `runtime/account_pool.py`、`runtime/account_lock.py` |

### 2.5 与容器化强相关、必须一起处理的配置风险

- `ensure_fernet_key()` 缺 key 时把新 key 写进**当前工作目录**的 `.env`;容器里若不注入
  `XIANYU_FERNET_KEY` 又不挂载 `.env`,每次重建都会换 key,已加密的 Cookie/Token 全部解不开。
- daemon 启动路径不跑 `alembic upgrade`;`init_db()` 的 docstring 写明仅供测试/冒烟。
- `http_host` / `mcp_host` 默认 `127.0.0.1`。
- 没有 `/health`;`daemon status` 恒为退出码 0;`doctor` 在「无活跃 daemon」时只是 WARN(退出码 0)。

## 三、目标架构

### 3.1 角色

单一镜像,按 `XIANYU_ROLES` 选择职责,可叠加:

- `api`:无状态,提供 FastAPI/MCP 与只读查询;
- `worker`:抢占账号租约并持有 WS 会话;
- `sampler`:每分钟巡检 + 采样,集群内单选。

最小落地可以一个容器同时承担 `api+worker`,`sampler` 单独一个容器或由编排层定时任务承担。

### 3.2 归属模型

- 实例身份沿用 `daemon_instances.instance_id`,新增租约到期时间。
- 账号归属:`accounts.owner_instance_id` / `owner_lease_until` / `owner_heartbeat_at`。
- 不变式:**任一时刻,一个账号最多一个未过期 owner**;owner 以短租约续租
  (建议心跳 10 秒,TTL = 3×心跳)。
- 抢占复用 `scheduler_queue.claim_due` 的 CAS 写法;接管前要求租约过期并超过冷却窗口。

### 3.3 数据模型改动

| 表 | 改动 | 说明 |
|---|---|---|
| `daemon_instances` | 新增 `lease_until`(或把「活跃」定义为 `last_heartbeat_at` 未过期) | 取代「谁最新谁活跃」 |
| `accounts` | 新增 `owner_instance_id`、`owner_lease_until`、`owner_heartbeat_at` | 账号分片的核心 |
| `transactional_outbox` | 新增 `lease_token`、`lease_owner`、`leased_until` 与索引 | 与 `scheduler_work` 同构 |
| 新增(可选) | `runtime_leases`(name, owner, lease_until) | sampler 单选、迁移门禁 |

迁移沿用现有 `batch_alter_table` 写法,三库 CI 会验证 SQLite/MySQL/Postgres 一致性。

### 3.4 账号接管协议(风险最高)

1. 候选副本发现账号租约过期(超过 TTL + 冷却);
2. 以 CAS 抢到租约,写审计 `account_lease_acquired`;
3. 丢弃本进程可能存在的旧 Worker,确保没有第二条连接;
4. 重新建立 WS 会话并续租;
5. 连续 N 次接管失败 → 进入现有风控熔断,交人工;
6. `XIANYU_TAKEOVER_REQUIRE_APPROVAL=true` 时,接管必须人工确认。

接管的风险是平台可能把「旧会话未断 + 新会话建立」判定为异常登录。缓解手段是 TTL 远大于心跳、
接管前留冷却窗口、接管次数上限与审计,以及可选人工确认。平台行为无法离线证明,**必须真机演练**。

### M3 接管协议与风控

状态:**已实施(2026-09-20),待真实多副本演练**。迁移 `c8e14f7a2d60` 增加一次性批准、
批准人、连续失败次数与最后失败时间;`claim_for_start` 在同一个 CAS 抢占点执行冷却和人工门禁。

## 五、CI 设计

| job | 内容 |
|---|---|
| `container-build` | 构建镜像 + `docker run --rm <image> alembic upgrade head` + `doctor` 冒烟 |
| `multi-replica` | Postgres + 两个容器,断言双健康、账号/outbox/采样租约单赢家,并验证强杀恢复 |
| 三库契约 | SQLite/MySQL/Postgres 分别断言 worker command 单次领取及既有 outbox 抢占 |
| 既有 `db-postgresql` | 复用,补充租约占用的并发用例 |

## 六、风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| 接管造成双会话 | 平台可能判定异常登录 | TTL ≫ 心跳、冷却窗口、接管上限、审计、可选人工确认 |
| 迁移期混合部署 | 旧单实例与新租约模式互相打架 | `XIANYU_RUNTIME_MODE` 开关,一次性切换,禁止混跑 |
| SQLite 共享卷 | 多副本共享 SQLite 会损坏 | 多副本强制 Postgres,SQLite 只做单副本模式 |
| Postgres 单点 | 数据库不可用即全停 | 交给编排层(托管 PG / 主从),不在本期范围 |
| 观测误报 | doctor/soak 仍按单实例判断 | M4 必须先于多副本上线 |
| 平台并发放大 | 副本变多后每进程 pacing 预算叠加 | 把配额口径改为「每账号全局」 |

回滚:代码用 `XIANYU_RUNTIME_MODE=legacy|lease` 切换;迁移保留 downgrade;M0 是纯新增文件。

### 8.2 对照项目做法(2026-09-20 只读核对)

| 维度 | Ydisks-Xianyu-Helper | xianyu-super-butler | 本项目现状 |
|---|---|---|---|
| Windows 托管 | SCM 服务(`golang.org/x/sys/windows/svc`)+ 托盘控制器 | 无,手动 `python Start.py` | 任务计划 Daemon + 每分钟 Watchdog |

| 健康面 | HTTP `/health` | HTTP `/health` + healthcheck | DB 心跳 + CLI,无 HTTP |
| 单实例 | 托盘命名互斥体 | 容器名唯一 | 文件锁 |
