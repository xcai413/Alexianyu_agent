# 容器化运行手册(单副本 daemon + 可选 Web/MCP)

> 状态:M0–M4 已实施,验收结论以 `docs/验证记录.md` 为准。
> 适用范围:当前 compose 文件的**单副本**自托管。多副本的租约、分片和接管控制已实现,
> 多副本编排与真实集群验收按 `docs/容器化与多副本方案.md` 的 M5 推进。

## 1. 前置条件

- Docker 24+ 与 Compose v2.24+(需要 `env_file.required` 支持;本仓库在 Compose v5.5.1 上验证)。
- 宿主 `.env`(至少要有 `XIANYU_FERNET_KEY`;可从 `.env.example` 复制)。
- 网络可访问 Docker Hub(拉 `postgres:16` 与 `python:3.11-slim`)。

## 2. 第一次部署

```bash
cp .env.example .env

# 1) 生成 Fernet 密钥,写进 .env 的 XIANYU_FERNET_KEY=
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# 2) 生成 Postgres 口令,写进 .env 的 POSTGRES_PASSWORD=
echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)" >> .env

# 3) 启动(首次会构建镜像)
docker compose up -d --build
docker compose logs -f app
```

容器入口按顺序执行:`alembic upgrade head` → `doctor` 门禁 → `xianyu-agent daemon run`。
daemon 启动路径**不会**自动迁移,所以不要绕过 entrypoint 直接跑二进制。

### 2.1 启动 Web 管理后台与 MCP

配置 `.env` 的管理员密码哈希和会话签名密钥后,启用 `console` profile:

```bash
uv run xianyu-agent web password-hash
# 将输出的整行写入 .env,保留包围哈希的单引号。
# 同时配置 XIANYU_WEB_SESSION_SECRET 为稳定的随机签名密钥。
docker compose --profile console up -d --build --wait
docker compose --profile console ps
```

浏览器入口为 `http://127.0.0.1:8090/`,MCP SSE 入口为 `/mcp`,同时保留历史 `/sse`。`web` 是独立服务,
由 Compose 的 `restart: unless-stopped` 管理;等待 `app` 完成迁移并健康后启动,不并行迁移共享库。
宿主8090已被开发服务占用时,在 `.env` 设 `XIANYU_WEB_HOST_PORT=18090` 后访问对应端口。

哈希中含 `$`,未加单引号会被 Compose 展开并导致登录失败。CLI 输出已提供单引号并禁用自动折行;
保留完整的一行。Compose 对单引号值的处理见
[Docker插值文档](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

端口只绑定宿主 `127.0.0.1`,远程内网操作可通过受控SSH隧道连接。此服务同时承载无需管理员会话的
Agent API与受会话保护的Web管理接口,不能直接把8090映射到公网。公网入口另需HTTPS、
`XIANYU_WEB_COOKIE_SECURE=true`及代理路径限制验收,当前编排未提供该公网验收证据。

### 2.2 保留现有 SQLite 数据

SQLite 使用独立编排文件,不要叠加默认PostgreSQL文件:

```bash
# 先备份原数据库、数据目录和 .env;保留原有 Fernet、SecretVault 与会话签名密钥。
# 维护窗口中确认原daemon已停止,同一运行目录不同时启动两套daemon。
docker compose -f compose.sqlite.yml --profile console up -d --build --wait
docker compose -f compose.sqlite.yml --profile console ps
```

文件明确将数据库设为 `/data/xianyu.db`,不会被默认Compose的PostgreSQL URL覆盖。宿主目录仍由
`XIANYU_HOST_DATA_DIR`指定,缺省为 `./data`;现有数据库文件名不同时先在隔离副本验证路径。
仅限单daemon实例,不执行 `--scale app`。首次容器启动会升级该库到源码head,因此先完成备份恢复验收。
默认PostgreSQL路径要求显式 `POSTGRES_PASSWORD`;两种路径均要求显式、稳定的 `XIANYU_FERNET_KEY`。

## 3. 验收命令

```bash
docker compose exec app xianyu-agent doctor
docker compose exec app xianyu-agent daemon status
docker compose exec app xianyu-agent pool start -a <账号>
docker compose exec app xianyu-agent daemon status
docker compose ps
```

期望:

- `doctor` 除 `windows_tasks`(非 Windows 跳过)外全 PASS,`migrations` 显示 `current == head`;
- `daemon status` 显示实例 `running`、心跳年龄 < 90 秒;
- `docker compose ps` 中 app 为 `healthy`。

容器健康检查请求 daemon 内嵌的 `http://127.0.0.1:8089/health`。该端点只提供健康摘要,
不开放 OpenAPI 或管理操作;数据库不可写、本实例心跳过期时返回 HTTP 503。

Web健康检查请求本服务无Cookie的会话查询并确认认证配置已就绪,随后读取会话撤销表。
HTTP存活但认证配置缺失、数据库不可用或撤销表缺失时,探针失败。失败输出仅包含异常类型。
生产配置不要设置 `XIANYU_SMOKE_ADMIN_PASSWORD`;`docker/web_console_smoke.py`只用于合成凭据的隔离验收。

## 4. 密钥与数据

- **`XIANYU_FERNET_KEY` 必须稳定**:它加密 Cookie 与 IM Token,换 key 等于全部账号要重新扫码。
  密钥由宿主 `.env` 注入,`.dockerignore` 已排除 `.env`,镜像里不存在该文件。
- `XIANYU_SECRET_MASTER_KEY` 加密发货 API 与 AI Provider 密钥。未设置时兼容复用
  `XIANYU_FERNET_KEY`;生产环境建议使用另一把 Fernet 密钥。已经写入 SecretVault 后不得直接换 key,
  应先按密钥轮换流程保留旧版本,否则现有引用无法解密。
- 数据目录默认绑在宿主 `./data`,可用 `XIANYU_HOST_DATA_DIR=/your/path` 覆盖;
  日志(`logs/`)、协议捕获(`captures/`)、二维码(`qr_logins/`)
  都在宿主可见。容器模式使用 Postgres,`xianyu.db` 不再参与运行。
- 用户级配置(回复模式、自动化模式、AI Key、守卫阈值等)继续从宿主 `.env` 读;
  `XIANYU_DATABASE_URL` 与 `XIANYU_DATA_DIR` 由 `compose.yml` 覆盖为容器内取值。
  `XIANYU_AUTOMATION_MODE` 在 compose 里默认取宿主值,缺省时回落 `observe`(不会自动外发)。
  `XIANYU_PLATFORM_AUTOMATION_INTERVAL_SECONDS` 控制擦亮/求花调度扫描间隔,默认 30 秒;它不绕过
  `observe`、真实校准和动作启用三道门禁。
  `XIANYU_ALERT_WEBHOOK_URL` 留空表示不发送任何外部通知;填 https 地址后,daemon 每
  `XIANYU_ALERT_INTERVAL_SECONDS`(默认 60 秒)把**新出现**的待人工处理事项 POST 过去。同一事项
  只发一次(靠 `alert_dispatches` 唯一键收敛,多副本也只有一个会发),地址要过出站守卫。

### 4.1 两种数据模式

| 模式 | 配置 | 适用 |
|---|---|---|
| Postgres(默认) | `compose.yml` 已内置 | 长期自托管、后续多副本 |
| SQLite(复用现有数据) | 独立使用 `compose.sqlite.yml`,保留数据目录绑定与原密钥 | 只想容器化、不想重新扫码 |

**切换模式前必须知道**:默认 `compose.yml` 给的是一个**全新的 Postgres 库**,里面没有账号、Cookie、消息与
订单。仓库没有 SQLite → Postgres 的数据迁移工具,所以默认路径下你需要重新扫码登录并重新
`item sync` / `order sync`。想保留现有账号数据,就用上面的 SQLite 模式,并确保用的是同一个
`XIANYU_FERNET_KEY`。

容器内进程以 UID 10001 运行,宿主数据目录必须对它可写:
`sudo chown -R 10001:10001 ./data`(或 `XIANYU_HOST_DATA_DIR` 指向的目录)。

## 5. 日常运维

完整备份恢复的范围、当前证据与操作边界见 [备份与恢复验收](备份与恢复验收.md)。
下面的数据库导出命令需要与数据文件和必要密钥一起保存；运营配置导出不能代替完整备份。

| 操作 | 命令 |
|---|---|
| 升级代码 | `git pull && docker compose up -d --build`(迁移在 entrypoint 内自动执行) |
| 看日志 | `docker compose logs -f app`;或宿主 `data/logs/xianyu-agent.log` |
| 重启应用 | `docker compose restart app` |
| 优雅停机 | `docker compose stop app`(SIGTERM,daemon 会走有序退出) |
| 备份数据库 | `docker compose exec postgres pg_dump -U xianyu xianyu > backup.sql` |
| 备份文件 | 直接复制宿主 `./data` |
| 恢复数据库 | `docker compose exec -T postgres psql -U xianyu xianyu < backup.sql` |

## 6. 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| entrypoint 报「数据目录不可写」 | bind mount 属主不是容器内 UID 10001 | `sudo chown -R 10001:10001 ./data` |
| app 一直是 `starting`/`unhealthy` | daemon 没起来或心跳过期 | `docker compose logs app`;核对账号 `desired_state` 与熔断状态 |
| `doctor` FAIL: migrations | 迁移没跑到 head | 维护窗口中执行 `docker compose run --rm app --version`;entrypoint会先迁移,不要把alembic当CLI子命令 |
| 扫码登录看不到二维码 | 二维码生成在容器内 `/data/qr_logins` | 看宿主 `./data/qr_logins/*.png` |
| Postgres 连接失败 | 口令改了但卷里还是旧库 | 首次部署后不要随意改 `POSTGRES_PASSWORD`;必要时删 `pgdata` 卷重建 |

## 7. 已知边界

- 单副本编排提供app与可选web服务;多副本仍使用独立 `compose.multi.yml`。
- Web/MCP 的独立服务、健康与重启检查使用合成凭据验收;真实数据恢复、目标入口和平台验收仍需单独完成。
- **容器内没有 Windows watchdog**:重启与自恢复由 compose `restart: unless-stopped` 承担;
  长稳采样已由所有 daemon 每分钟竞争数据库租约后执行,不需要另起 Windows watchdog。
- 多副本必须共享 Postgres/MySQL,并为每个副本提供独立 `/data`;不得让多个副本共享 SQLite。

## 8. 接管控制(M3)

- 默认自动接管:`XIANYU_TAKEOVER_REQUIRE_APPROVAL=false`。旧副本强杀后,候选副本需等账号租约
  TTL 60 秒再加冷却 120 秒,然后才能 CAS 抢占。
- 人工批准模式:在所有 app 副本设置 `XIANYU_TAKEOVER_REQUIRE_APPROVAL=true`,候选副本只记录
  `takeover_approval_required`;操作员执行
  `xianyu-agent pool takeover-approve -a <账号>` 后才允许抢占。
- `pool status` 的 `takeover` 列显示批准和连续失败次数。可用
  `pool takeover-revoke -a <账号>` 撤销尚未使用的批准。
- `XIANYU_TAKEOVER_MAX_FAILURES` 默认 3。连续接管启动失败达到上限后,账号进入
  `TAKEOVER_FAILURE_LIMIT` 人工恢复闸并停止期望运行;排查凭据和平台状态后执行一次成功的
  `auth refresh -a <账号>`,再重新 `pool start`。

## 9. 双副本部署与空账号验收(M5)

双副本使用专用编排文件。migrate 服务只运行一次迁移;两个 app 跳过迁移、等待 migrate 成功后
启动,并分别使用独立命名卷。不要用主 `compose.yml` 的 app bind mount直接 `--scale`。

```bash
docker compose -f compose.multi.yml up -d --build
docker compose -f compose.multi.yml ps
docker compose -f compose.multi.yml exec -T app-a \
  python /app/docker/multi_replica_smoke.py
```

探针成功时输出 JSON:`app_a.status`/`app_b.status` 都是 `healthy`,
`database.active_daemons` 有两个不同实例,`account_lease_winners` 和
`outbox_lease_winners`、`runtime_lease_winners` 都等于 1。

无账号故障恢复演练:

```bash
docker compose -f compose.multi.yml kill app-b
docker compose -f compose.multi.yml up -d app-b
# 旧实例租约最长 60 秒才过期;随后重复执行上面的 multi_replica_smoke.py
```

清理验收栈:`docker compose -f compose.multi.yml down -v`。`-v` 会删除该栈的 Postgres 和两个
app 数据卷,只用于测试环境。带真实账号的接管、滚动升级和 24 小时长稳按
`docs/待真实验证清单.md` D3–D6 执行。
